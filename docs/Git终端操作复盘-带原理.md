## 一、先建立心智模型(最重要,先懂这个再看命令)

Git 协作的本质:**同一个项目有很多份拷贝,靠"推 / 拉"来同步**。

```
        Gitee 服务器上的团队仓库(唯一的"官方"版本,大家共享)
                    ▲  │
             push  │  │  clone / pull
            (上传) │  │ (下载)
                    │  ▼
        你电脑上的本地拷贝(你在这里改文件、干活)
             └─ 里面又分很多"分支":master 是主线,你在自己的分支上改
```

一条主线记牢:**克隆下来 → 开自己的分支 → 改文件 → 存档(commit)→ 上传(push)→ 申请合并(PR)**

## 二、再懂一个关键:git 里文件要走"三个区"

`git add` 和 `git commit` 到底在干嘛?因为你的改动会经过三个区:

| 区 | 是什么 | 对应命令 |
|---|---|---|
| **工作区** | 你实际编辑文件的文件夹 | (你直接改文件) |
| **暂存区** | "我准备打包这些改动"的候选清单 | `git add` 把改动放进来 |
| **版本库** | 正式存档的历史 | `git commit` 把暂存区封存成一次快照 |

**为什么分 add 和 commit 两步?** 因为你可能改了 10 个文件,但只想把其中 3 个作为这一次提交。
`add` 让你**挑**,`commit` 让你**封存**。挑好了再拍板,干净利落。

## 三、逐步复盘(你实际敲过的命令 + 原理)

### 阶段 0:确认工具能用
```
git --version
```
- **原理**:git 是命令行工具,先确认装好了、能调用。
- **为什么**:后面所有操作都靠它,先验明正身,免得白忙。

### 阶段 1:把团队仓库"搬"到本地
```
cd ~/Desktop
git clone https://gitee.com/huangxinyi2007/personalized-code-assistant.git
```
- **原理**:`cd` 是切换目录(进桌面);`clone` 是把服务器上**整个仓库(含全部历史)**完整下载一份到本地。
- **为什么**:git 是"分布式"的——你不能直接在服务器上改,必须先拿一份到本地,在本地改。

### 阶段 2:站到自己的分支上
```
cd personalized-code-assistant
git switch feat/fnl-error-cases
git branch
```
- **原理**:`git switch` 切换分支;`git branch` 列出分支,**前面带 `*` 的是你当前所在的**。
- **为什么不直接改 master**:① 黄新意明令不许;② 多人同时动主线会乱套;③ 在自己分支上改,改坏了也不影响别人,**审核通过再合并才安全**。
- **细节**:这个分支已经存在(黄新意建好了),所以用 `switch` **不加 `-c`**;如果是要新建分支,才用 `switch -c 新分支名`。

### 阶段 3:把自己的文件弄进来(这里你踩了个坑,正好学到东西)

你的文件在你自己的 Gitee 仓库 `111` 里,所以先把它也克隆到本地,然后想复制过来。
但第一次复制报了 `No such file or directory`。

- **坑的原理**:`git clone` **默认只给你"默认分支"(main)**,而你的文件其实在另一条分支
  `claude/session-2lvlke` 上。main 是空的,所以找不到文件。
- **怎么解的**:
```
git branch -a                       # 列出所有分支(含服务器上的 remotes/origin/...)
git switch claude/session-2lvlke    # 切到真正有文件的那条分支
ls demo                             # 文件出现了
```
- **教训**:clone 后如果没看到预期文件,先 `git branch -a` 看看东西是不是在别的分支上。

然后复制文件进团队仓库:
```
cd ~/Desktop/personalized-code-assistant
mkdir -p ./demo/cases
cp ~/Desktop/111/demo/cases/cases.py ./demo/cases/
cp ~/Desktop/111/demo/run_case_check.py ./demo/
```
- **原理**:`mkdir -p` 建目录(`-p` = 不存在就建、已存在也不报错);`cp` 复制文件。
  我们把"源仓库 111"里的文件复制进"团队仓库"的工作区。
- **为什么只复制这两个**:这是**你负责的交付物**(错误案例 + 验证脚本),不碰别人的文件,职责清晰。

### 阶段 4:让 git 记录并上传
```
git status                 # 看变化:红色 = 未跟踪的新文件
git add demo/              # 把新文件放进暂存区
git status                 # 再看:绿色 = 已暂存,准备提交
git commit -m "demo: 提交3个Python错误案例、技术诊断与验证方法"
git push origin feat/fnl-error-cases
```
- **原理串起来**:改文件(工作区)→ `add`(暂存)→ `commit`(本地存档快照)→ `push`(上传服务器)。
- **为什么 commit 后还要 push**:`commit` 只存在**你本地电脑**上,`push` 才让**服务器和队友**看得到。
- **坑**:`commit` 时出现 `>` 一直等你 —— 因为中文输入法把英文引号 `"` 变成了**全角引号 `"`**,
  bash 不认,以为引号没闭合。**`Ctrl + C` 取消,把输入法切英文再打引号**就好。

### 阶段 5:发起合并申请(Pull Request)
在 Gitee 网页点"创建 Pull Request",源分支 `feat/fnl-error-cases` → 目标分支 `master`,填标题说明,提交。
- **原理**:PR = "我申请把我的分支合并进主线,请你先审再合"。
- **为什么不自己直接合进 master**:团队规矩是负责人(黄新意)审核后才合,保证主线质量。
  所以你 `push` 到自己分支 + 发 PR,**合并权在他**——页面上"暂不能合并"就是在等他点通过,不是报错。

## 四、以后再来一遍(极简清单,存着照抄)

```
# 1. 拿到最新的团队仓库(第一次用 clone,以后同一个文件夹里用 pull 更新)
git clone <团队仓库地址>
cd <仓库文件夹>

# 2. 开 / 切到自己的任务分支
git switch -c <你的分支名>       # 全新分支用 -c;分支已存在就去掉 -c

# 3. 改文件 / 放文件……(在文件夹里正常操作)

# 4. 存档并上传
git status                       # 看看改了啥
git add .                        # 把所有改动放进暂存区
git commit -m "说明这次改了什么"  # 存档(引号一定用英文半角!)
git push origin <你的分支名>      # 上传到服务器

# 5. 去 Gitee 网页发 Pull Request,等负责人审核合并
```

## 五、你今天真正学会的 5 个核心概念

1. **仓库 / 克隆**:项目的完整拷贝,拿到本地才能干活。
2. **分支**:平行开发线,保护主线 master,改坏了不连累别人。
3. **三个区 + add/commit**:工作区改 → 暂存区挑 → 版本库封存快照。
4. **远程 origin + push**:把本地的存档同步回服务器,队友才看得到。
5. **Pull Request**:申请合并 + 审核门槛,主线质量有人把关。

## 六、你踩过的两个坑(记住就不会再犯)

| 坑 | 现象 | 原因 | 解法 |
|---|---|---|---|
| 文件在别的分支 | `cp` 报 No such file | `clone` 默认只给 main,文件在别的分支 | `git branch -a` 看,`git switch` 切过去 |
| 引号变全角 | `commit` 后卡在 `>` | 中文输入法把 `"` 变成 `"` | `Ctrl+C` 取消,输入法切英文再打引号 |
