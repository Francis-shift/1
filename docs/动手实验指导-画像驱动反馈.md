## 第 1 步:找一个真实的学生错误程序(不要自己编)

用真实数据更有说服力。这是 Refactory 数据集里的 `wrong_1_001.py`:

```python
def search(x, seq):
    for i, e in enumerate(seq):
        if x < e:
            return i
    return len(seq)
```

题目 **Sequential Search**:在**已排序**序列 seq 里,返回 x 应该插入的位置
(使序列仍然有序)。等价于"seq 里有几个元素小于 x"。

👉 **先自己想 30 秒**:这段哪里可能错?(想不出来也没关系,下一步让电脑告诉你)

---

## 第 2 步:亲手运行它,亲眼看它错

新建 `try1.py`:

```python
def search(x, seq):
    for i, e in enumerate(seq):
        if x < e:
            return i
    return len(seq)

# 测试:3 应该插在位置 1(因为 seq = (1,3,5),3 排在第 1 个位置)
print("结果:", search(3, (1, 3, 5)))
print("期望:", 1)
```

运行:`python3 try1.py`

✅ **检查点**:你应该看到 `结果: 2`、`期望: 1` —— **它算错了!**

👉 **想清楚为什么**:当 x=3 走到 e=3 时,`x < e` 就是 `3 < 3`,是 False,
所以跳过了,一直走到 e=5 才返回 2。问题就是:`<` **漏掉了"相等"这种情况**。
这类错误叫**边界条件错误**。

> 这一步你干的事,就是 BRAFAR 流水线里 **Fault Locator(故障定位)** 干的事:
> 用测试用例把"哪里导致了错误结果"找出来。

## 第 3 步:亲手把"诊断"写成结构化的数据

你已经看懂错在哪了。把它整理成一个字典——这就是 BRAFAR 诊断的"产物",
后面要交给"画像层"去因人而异地讲:

```python
diag = {
    "错误类型": "边界条件错误",
    "粗略位置": "循环里的比较判断",     # 给新手:只说"在这一带"
    "出错行号": 3,                      # 给进阶/熟练:精确到行
    "相关概念": "< 和 <= 在边界(相等)时行为不同,查找类问题要小心 = 这个临界点",
    "最小改法": "把 < 改成 <=",
}
```

👉 **自己想想**:这 5 个字段,哪些适合讲给新手、哪些适合讲给高手?
(这个"该给谁看哪些字段"的判断,正是下一步画像要做的事。)

---

## 第 4 步:亲手写 3 份画像(先用最简单的"开关"形式)

```python
profiles = {
    "熟练型": {"给改法": False, "补概念": False, "定位": "粗"},
    "进阶型": {"给改法": False, "补概念": False, "定位": "行号"},
    "新手型": {"给改法": True,  "补概念": True,  "定位": "行号"},
}
```

三个开关:给不给改法提示、补不补概念、定位给粗的还是给行号。
**这就是"画像"最朴素的样子**——一组决定"反馈怎么给"的参数。

⚠️ **注意方向,它和直觉相反**:**粗定位是给熟练者的,不是给新手的**。
能力强的人自己能把范围收敛下去,给个方向就够,讲太细反而打断他;
能力弱的人才需要具体行号、概念解释和改法提示,只给"在这一带"对他等于没说。
(团队仓库 `demo/feedback_rules.py` 的 L1—L4 就是这个方向。)

---

## 第 5 步:亲手写"组装反馈"的函数(这是整个 demo 的心脏)

同一个 `diag`,按画像的开关拼出不同的话:

```python
def make_feedback(diag, p):
    lines = []
    # 定位:粗 还是 行号
    if p["定位"] == "粗":
        lines.append(f"问题在「{diag['粗略位置']}」附近,自己找找是哪一行")
    else:
        lines.append(f"问题在第 {diag['出错行号']} 行")
    # 补概念?
    if p["补概念"]:
        lines.append(f"相关概念:{diag['相关概念']}")
    # 给改法提示?
    if p["给改法"]:
        lines.append(f"改法:{diag['最小改法']}")
    else:
        lines.append("想想该怎么改,自己试一版再运行")
    return "\n".join(lines)
```

👉 看懂这个函数:它没有三段写死的话,而是**根据开关一段一段拼**。
开关变了,拼出来的话就变了。

---

## 第 6 步:跑起来,亲眼看"同题不同答"

把第 3~5 步的代码接在一起,末尾加上:

```python
for name, p in profiles.items():
    print(f"===== {name} =====")
    print(make_feedback(diag, p))
    print()
```

运行,✅ **检查点** 你应该看到三段明显不同的反馈:

```
===== 熟练型 =====
问题在「循环里的比较判断」附近,自己找找是哪一行
想想该怎么改,自己试一版再运行

===== 进阶型 =====
问题在第 3 行
想想该怎么改,自己试一版再运行

===== 新手型 =====
问题在第 3 行
相关概念:< 和 <= 在边界(相等)时行为不同,查找类问题要小心 = 这个临界点
改法:把 < 改成 <=
```

🎉 **到这里,你就亲手验证了整个项目最核心的一句话:同题不同答。**
熟练型只拿到大致方向,自己去收敛;进阶型拿到行号但仍要自己想改法;
新手型行号、概念、改法提示都给到——**帮助力度随能力递减,不是递增**。

## 第 7 步:自己改一改,确认"画像真的在起作用"

每改一处就跑一次,看输出怎么变:

1. 把"熟练型"的 `"给改法"` 改成 `True` → 看它的反馈多了哪一行。
2. 给 `profiles` 加第 4 份画像:
   `"卡很久型": {"给改法": True, "补概念": True, "定位": "行号"}` → 看它拼出什么。
   (这对应团队规则里的 L4:不看能力,只看"是不是卡太久了"。)
3. 把某个画像的三个开关全设成一样,你会发现它和另一个画像输出相同——
   **这说明:是"开关(画像)"在决定输出,不是别的。**

## 你手写的这版 ↔ 仓库正式版(demo/)的对应关系

| 你手写的 | 仓库正式版 | 正式版多做了什么 |
|---|---|---|
| 1 个错误 diag | `demo/cases/cases.py` 里 3 个案例 | 3 类错误,且都用测试用例**验证过真的会失败** |
| 3 个"开关"画像 | `demo/profiles_and_rules.py` 的 PROFILES | 升级为 K/D/H/E 四维 |
| 手动设开关 | 同文件的 6 条 RULES | 由画像四维**自动算**出开关(风格四旋钮) |
| make_feedback | `demo/demo.py` 的 compose_feedback | 多了语气、解释深度两个旋钮 |
| 肉眼看不同 | demo.py 结尾 | **机器断言**三份反馈两两不同 |

**所以正式版不是更"高级",只是把你这版的每个部件都做扎实、做可扩展了。**
你手写的这 30 行,就是它的内核。

## 做完之后,你就能对着汇合会讲清楚三件事

1. **数据从哪来**:真实学生错误程序(Refactory),不是编的。
2. **画像怎么改变反馈**:画像是一组开关/参数,反馈按它逐段组装,改画像就改输出。
3. **和 BRAFAR 的关系**:BRAFAR 负责"诊断出错在哪、最小怎么改"(产出 diag),
   我们负责"这份 diag 该怎么讲给这个人"(画像驱动)。
