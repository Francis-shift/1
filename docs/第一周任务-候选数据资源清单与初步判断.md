## 一、概念澄清:user persona 与 user profile 的区别

| | User Persona(用户角色) | User Profile(用户画像/档案) |
|---|---|---|
| 本质 | 基于调研**虚构**出的典型用户原型 | 系统为**每个真实用户**维护的结构化数据 |
| 内容 | 名字、背景故事、目标、痛点、使用场景 | 属性、行为特征、标签、偏好、统计指标 |
| 数量 | 一个产品通常只有 3~5 个 persona,代表几类用户 | 每个用户一份,成千上万 |
| 性质 | 定性、静态(设计阶段产出后基本不变) | 定量、**动态更新**(随行为数据持续变化) |
| 用途 | 设计阶段对齐团队认知、指导功能取舍 | 运行时驱动个性化决策(推荐、适配、辅助) |

**对本项目的含义**:
- 申报书里的"四维学习者画像(K/D/H/E)"是 **user profile**——每个学习者一份、由行为数据驱动、随学习过程更新、直接作为回答策略控制器的输入。
- **persona 也有用**,但用在别处:定义目标用户类型("新手型 / 进阶型 / 熟练型"本质上是把 profile 聚类后 persona 化的标签)、设计用户调研问卷、GQM 实验分组。
- 注意术语陷阱:VirtualME 论文里说的 "developer persona" 实际是标签化的 profile(技术栈/能力/行为习惯/学习风格四维),和 UX 领域的 persona 不是一回事。读文献时按上下文判断。

## 二、候选数据资源清单

按数据类型分四组。每条给出:内容与字段 → 规模 → 获取方式 → 能支持的画像维度(K 知识基础 / D 调试与执行 / H 求助与交互 / E 学习演化)→ 局限。

### A 组:IDE 行为日志类

#### A1. Blackbox / Blackbox Mini(BlueJ,Java)
- **内容**:BlueJ 初学者 Java IDE 中自愿用户的源码编辑、编译结果、调试器等工具使用事件,自 2013 年持续采集至今。
- **规模**:主库为超大规模(百万级用户);Blackbox Mini 是精选子集(2013 年首批约百万事件),schema 与主库一致,便于先在小库上调试查询再放大。
- **获取**:计算机教育研究者**申请制**(免费、永久访问),非即下即用。官网经由 bluej.org / academiccomputing 博客申请。
- **支持维度**:D(编译错误、修复过程)、K(错误类型分布)、E(数据跨度多年,可看长期演化)。
- **局限**:Java 而非 Python;无 AI 求助数据;申请有周期;数据在其服务器上查询,不能整库下载。

#### A2. KaVE FeedBaG++ 数据集(Visual Studio)
- **内容**:Visual Studio + ReSharper 插件 FeedBaG 采集的"增强事件流"(Enriched Event Stream):IDE 中所有命令调用 + 上下文信息,含编辑器代码快照(SST 格式)、测试运行、调试等。MSR 2018 挖掘挑战赛官方数据。
- **规模**:约 1100 万事件、1.5 万工作小时、81 名开发者。
- **获取**:**直接下载**,https://www.kave.cc/datasets ,配套 CARET 工具读取。
- **支持维度**:D(调试/测试行为)、H 的部分(工具使用习惯)。
- **局限**:对象是职业开发者而非编程学习者;C#/VS 生态;无求助与学习任务上下文。**主要价值是给我们的 VS Code 插件设计"该采什么事件、事件 schema 长什么样"提供成熟参照**。

#### A3. VirtualME(申报书引用文献[4],FSE 2026)
- **内容**:IDE 内嵌数据基础设施:日志级行为提取 → 多智能体管线聚合为任务级行为 → 规则引擎产出四维开发者画像(技术栈、能力、行为习惯、学习风格);并构建了含真实开发者轨迹的多仓库个性化问答 benchmark。
- **获取**:官网 https://virtualme26.github.io/VirtualME (目前页面内容极少,benchmark 实际开放程度**待确认**;论文 arXiv:2605.29372)。建议由老师或负责人邮件联系作者(南大团队,与 BRAFAR 同源)索取。
- **支持维度**:与我们的 K/D/H/E 架构**最同构**,其"日志→任务级行为→画像→个性化问答"正是我们要走的路线。
- **局限**:面向职业开发者;数据可得性未落实,当前只能作为方法参照 + 跟进项。

### B 组:学生编程过程 / 提交序列类

#### B1. CodeWorkout / CSEDM Data Challenge 数据集(ProgSnap2,Java)★推荐
- **内容**:美国某公立大学 CS1 课程 2019 春/秋两学期,学生在 CodeWorkout 平台上 50 道编程题的完整提交过程。ProgSnap2 格式,MainTable.csv 含全部过程事件(Run.Program、Compile、Compile.Error 等),附提交得分(通过测试百分比)、编译报错信息。
- **规模**:春 329 人 + 秋 490 人,每学期 6.5 万+ 次提交。
- **获取**:**需要账号,下载入口待落实**(2026-07-17 实测勘误):CSEDM Data Challenge 官网(sites.google.com/ncsu.edu/csedm-dc-2021/dataset)现已跳转 Google 登录页;GitHub 上的 YangAzure/CSEDMDataChallenge 仓库**只有示例代码没有数据**;数据的官方托管处是 PSLC DataShop(datashop.web.cmu.edu,需免费注册账号)。本轮未完成数据层验证,字段描述来自 ProgSnap2 规范与挑战赛论文,待注册 DataShop 后核对。
- **支持维度**:K(按题目/知识点的正确率)、D(编译错误类型、重复报错、修复轨迹)、**E(整学期纵向数据,少有的能支撑"学习演化"的公开集)**。
- **局限**:Java;只有提交粒度,无 IDE 内编辑细节;无求助数据。

#### B2. FalconCode(Python)★推荐
- **内容**:美国空军学院 CS1 课程 5 个学期、800+ 编程作业的学生代码快照(每次运行前自动上传),附每题题面、测试用例、所需技能标签,已脱敏。
- **规模**:150 万+ Python 程序、2000+ 学生。
- **获取**:**门控访问,不是免申请直接下载**(2026-07-17 实测勘误):HuggingFace 版 https://huggingface.co/datasets/koutch/falcon_code 需要注册登录、同意数据使用条件并共享联系信息后才能访问文件;官方渠道为研究用途申请制。需团队成员用个人账号完成授权。
- **支持维度**:K(技能标签 × 对错,可直接算知识点掌握度)、D(运行前快照序列可复原试错过程)、E(跨学期)。
- **局限**:快照粒度介于键击和提交之间;无求助数据。**语言对口(Python)+ 带技能标签,是构建 K 维画像最顺手的公开数据**。

#### B3. JEDM 两个公开 CS1 键击数据集(Edwards & Hart)
- **内容**:键击级(keystroke-level)编程过程日志,ProgSnap2 格式,含丰富元数据,完全去标识化。
- **规模**:小集 44 人 × 8 次作业;大集 505 人 × 5 次作业。
- **获取**:公开,见 JEDM 期刊文章页(jedm.educationaldatamining.org, "Review of CSEDM Data and Introduction of Two Public CS1 Keystroke Datasets")。
- **支持维度**:D(最细粒度的试错/停顿/修改节奏)、E(多次作业纵向)。
- **局限**:规模小;分析成本高。适合做"高层学习行为识别"算法的验证集。

#### B4. IBM Project CodeNet
- **内容**:两个在线评测网站(AIZU/AtCoder)的提交,4053 道题,每份提交带状态(通过/错误答案/超时/超内存等)、CPU 时间、内存、代码体积等标注。
- **规模**:1391 万份提交,55 种语言,53.6% 通过。
- **获取**:**直接下载**,https://github.com/IBM/Project_CodeNet (数据托管在 DAX,DOI: 10.5281/zenodo.4814770)。
- **支持维度**:K/D 的素材库(海量"错误代码-正确代码"对、错误类型分布)。
- **局限**:竞赛/OJ 场景,非课程学习过程;用户纵向轨迹弱。主要当**素材库**用(如给个性化反馈生成攒题目和错误样例),不当画像数据用。

### C 组:错误-正确代码与测试用例类(反馈/修复验证)

#### C1. Refactory benchmark(NUS,Python)★推荐
- **内容**:新加坡国立大学 Python 入门课 5 个作业:每题含教师参考实现 reference.py、完整测试套件(input_x.txt/output_x.txt)、学生正确提交 correct_*.py、学生错误提交 wrong_*.py。
- **规模**:2442 份正确 + 1783 份错误提交,361 名学生。
- **获取**:**直接下载**,https://github.com/githubhuyang/refactory 。
- **支持维度**:本身不是画像数据,而是**"个性化反馈生成"模块的标准试验场**——BRAFAR 论文的全部实验就在这套数据上做的。
- **局限**:无时间序列、无学生纵向信息。

#### C2. BRAFAR 开源工具(配套 C1)
- **内容**:老师指定论文的官方实现,输入"错误程序 + 正确程序集 + 测试用例",输出最小修复补丁。
- **获取**:https://github.com/LinnaX7/brafar-python 。
- **用途**:可直接作为我们系统"反馈生成"的基线组件:BRAFAR 负责"改哪里、怎么改",我们的画像层负责"以什么粒度/形式呈现给不同水平的学习者"——两者拼起来就是初版智能辅助的核心链路。

### D 组:求助 / AI 交互类

#### D1. CS1QA(NAACL 2022,Python)★推荐
- **内容**:韩国 KAIST Python 入门课在线聊天记录:9237 个标注问答对(每问附学生当时的代码 + 相关代码行区间 + 9 类问题类型标签)+ 17698 个未标注聊天会话。
- **获取**(2026-07-17 实测确认):标注问答对(`data/final/`,jsonl)与 17698 个聊天会话(`data/chat_cleaned.json`,71MB)**均可从 GitHub 直接下载**:https://github.com/cyoon47/cs1qa ;**学生代码全量数据**因体积未上传,需邮件联系作者(changyoon.lee@kaist.ac.kr)。实测字段:标注集 `labNo, taskNo, questioner, question, code, startLine, endLine, questionType, answer`;聊天集含匿名学生 ID、起止时间戳和逐条消息,可直接按学生聚合。
- **支持维度**:**H(求助与交互)维度目前最对口的公开数据**——问题类型、提问方式、代码上下文俱全;也可给 K 维提供"哪里不懂"信号。
- **局限**:学生问的是**人类助教**而非 AI;英文/韩文语境。

#### D2. DevGPT(MSR 2024 挖掘挑战赛)
- **内容**:开发者在 GitHub(issue/PR/commit/discussion)和 Hacker News 中分享的真实 ChatGPT 对话链接及全文:提示词、回复、代码块、token 数、模型版本,并关联到对应的开发工件。六个时间快照。
- **规模**:16129 个 prompt、9785 个代码片段。
- **获取**:**直接下载**,https://github.com/NAIST-SE/DevGPT (Zenodo DOI: 10.5281/zenodo.10086809)。
- **支持维度**:H(真实"人-AI"对话:提问方式、追问深度、要完整代码还是要思路)。
- **局限**:对象是开发者而非编程学习者;对话是自愿分享的,有幸存者偏差。

## 四、缺口分析

1. **本轮检索尚未发现同时覆盖四个维度**(IDE 行为 + 报错日志 + AI 求助 + 长期演化)**的公开数据集**(一次调研不能断言全网不存在,但至少主流渠道没有现成的)。这与申报书判断的研究空白一致,也说明**自研 VS Code 插件采集最终不可替代**——公开数据只能分维度拼接和先行验证。
2. **H 维度缺"编程学习者 × AI 助手"的真实日志**:CS1QA 是学生问人类助教,DevGPT 是开发者问 ChatGPT,两者拼起来只能近似。我们插件的内置问答通道将采到的正是这块空白数据——这本身就是项目的数据贡献点。
3. **E 维度只有 CodeWorkout、FalconCode、Blackbox 能撑**(有整学期以上的纵向轨迹),其余数据集多为单点快照。
4. **语言错位**:过程数据最丰富的 Blackbox/CodeWorkout 是 Java;好在 FalconCode、Refactory、CS1QA 都是 Python,与我们的目标场景(程序设计课,Python 为主)对得上。
5. VirtualME 是与我们架构最接近的工作,但其 benchmark 开放程度未落实,**建议请石老师或黄新意出面邮件联系作者**(南京大学团队,与 BRAFAR 作者同组)。

## 五、初步判断与建议(结论)

1. **公开数据足以支撑暑期"模拟画像 + 初版链路"阶段,不必等插件采集**。这与 7 月 9 日会议"各模块不必串行等待"的结论一致。第六节的实测证实:Refactory、BRAFAR、CS1QA 已**分别**完成数据层和工具层验证,可以支撑后续端到端集成;但"画像 → 策略选择 → 修复/反馈生成"的完整链路**尚未连通**,那是下一阶段(智能 IDE 初版)的工作,不在本任务范围内。
2. **推荐的最小组合**:
   - **Refactory + BRAFAR 工具**(✓已实测) → 跑通"错误程序 → 定位 → 修复建议"再叠加画像分级呈现,验证个性化反馈;
   - **CS1QA**(✓已实测) → 归纳 H 维的问题类型体系和求助偏好规则,反哺我们内置问答通道的日志 schema 设计;
   - **FalconCode**(待 HF 账号授权) → 构建 K 维画像(技能标签 × 对错)和 D 维特征(快照序列试错分析),Python 对口;
   - **CodeWorkout/CSEDM**(待 DataShop 注册) → 验证 E 维(整学期错误率下降趋势等演化指标)的计算方法。
3. **KaVE 事件 schema 值得李镐泓做插件时参照**(该采哪些事件、上下文怎么带)。
4. 合规注意:以上均限研究用途,引用需注明来源;Blackbox、FalconCode 官方渠道需申请;CS1QA 作者明确要求不得滥用数据中可能残留的个人信息;二次分发前查许可证。
5. 待办(需要真人账号,本轮无法代办):① 某成员用个人 HuggingFace 账号完成 FalconCode 授权并抽读一条记录;② 注册 PSLC DataShop 下载 CodeWorkout S19/F19,核对 MainTable.csv 字段;③ 邮件联系 CS1QA 作者获取代码全量数据(可选);④ 请老师/负责人邮件 VirtualME 作者确认 benchmark 开放情况。

## 六、数据层验证记录(2026-07-17 实测)

> 验证环境:Ubuntu 24.04,Python 3.11.15。验证脚本已入库:`scripts/verify_refactory.py`、`scripts/verify_cs1qa.py`(仅标准库,学生程序在独立子进程中带超时执行),环境与数据获取步骤、运行命令、预期输出见 `scripts/README.md`,示例输出见 `scripts/output_refactory_features.json`。
> 验证的边界:以下各条是对**单个资源**的数据层/工具层验证;"CS1QA 画像 → 策略选择 → BRAFAR 修复 → 差异化反馈"的端到端链路尚未搭建。

### 6.1 Refactory benchmark:已下载、字段与规模属实、可直接运行

- 克隆仓库(仅 3.5MB,数据在 data.zip 内),解压得 question_1~5,目录结构与 README 一致(`code/reference|correct|wrong` + `ans/input_xxx.txt|output_xxx.txt`)。
- question_1 实测:reference 1 份、correct **768** 份、wrong **575** 份、测试用例 **11** 个——与 BRAFAR 论文 Table 3 第一行完全一致。
- 参考程序通过全部 11 个测试;对前 100 个错误程序批量执行测试(见脚本),**跑通即证明"错误程序+测试用例"开箱可用**。
- **口径注意**:wrong_x_yyy.py 文件名不含学生 ID,同一学生的多次提交串不起来,所以 6.4 表中由此算出的是**提交级候选特征**,不是学习者级画像;学习者级聚合要靠 CS1QA(匿名学生 ID)或 CodeWorkout(SubjectID)。
- 注意:`refactory_online.csv` 是原作者的**实验结果表**(修复耗时、补丁大小等),不是学生过程数据,不要误当行为日志用。

### 6.2 BRAFAR 工具:能安装、能修复,输出可直接用作反馈原料

- 依赖为老版本包(fastcache 等 C 扩展),新 setuptools 下编译失败;**解决办法:venv 中先装 `setuptools==59.8.0` 再装 requirements**,Python 3.11 可用。此坑已踩平,团队直接照做即可。
- 用 5 个错误程序的迷你数据集运行 `run.py -s 0`(仅用参考程序做修复源):**烟雾测试 5/5 成功**,单个耗时 0.02~0.19 秒,输出 CSV 含修复代码、补丁相对大小 RPS、各阶段耗时。烟雾测试只证明**可安装、可调用、能输出修复结果**,不作为修复率评估;整体修复率以论文报告的 98.5%(1783 程序)为准,如需自证可对全量 data 目录重跑。
- 修复示例(wrong_1_001.py):学生写 `if x < e: return i`,BRAFAR 修为 `if x <= seq[i]: return i`——最小补丁、保留学生循环思路,正是"个性化反馈"想要的原料。

### 6.3 CS1QA:已下载、字段属实、算出了第一批真实 H 维候选特征

- 标注数据 train+dev+test 共 **9237 条**,与论文口径一致(另有增强训练集 5907 条,注意别混入统计)。实测字段:`labNo, taskNo, questioner, question, code, startLine, endLine, questionType, answer`。
- 问题类型 9 类实测分布:variable 1943 / task 1322 / algorithm 1194 / logical 1060 / error 959 / code_explain 940 / usage 811 / reasoning 799 / code_understanding 209。提问者:学生 5555 vs 助教 3682。
- 未标注聊天 `chat_cleaned.json`(71MB,GitHub 可直接下载)含 **17698 个会话、1317 名匿名学生**,有时间戳和逐条消息。
- **第一批真实 H 维候选特征已算出**(脚本输出,口径如下):
  - 人均求助会话 **13.4** 次(最高 50 次)——指**整个数据集观察期(约一学期)** 内的总会话数,不是每周频率;
  - 按学生等权计算的会话内平均消息数 **17.9** 条——先计算每名学生自己的"消息数/会话数",再对学生取等权平均,统计包含**学生与助教双方**全部消息,不等于追问深度;
  - 按学生等权计算的会话内**学生侧**消息数 **8.9** 条——采用同样的宏平均口径,只数学生发出的消息,可作为提问/追问轮次的**近似上界**(其中还混有粘贴代码等非提问消息);更严格的"追问深度"(首问后追加提问的次数)需要对消息做提问识别,留待正式管线。
  - 已演示按学生输出"求助频率/交互密度"特征——CS1QA 有匿名学生 ID,是本轮唯一能落到"每个学习者一份 profile"粒度的已验证数据。
